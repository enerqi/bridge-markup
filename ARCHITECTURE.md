# bridge-markup implementation notes

**Read `~/dev/bml/ARCHITECTURE.md` first if you want to know how BML parsing *works*.** That document
explains the reference implementation — why it classifies a block at a time instead of using a
grammar, how the bid-table indentation rules arrived at their present shape, what each regex is
defending against. All of that is inherited here and is not repeated.

**This document covers the PORT**: the shape the Odin takes, where it deliberately differs, what is
bug-compatible on purpose, and how to work on it without breaking the one guarantee that matters.

---

## 1. The guarantee

Byte-identical html to the python reference, for the whole bridge corpus.

```
just parity        →  IDENTICAL 19/19
```

Everything else in this document is downstream of that. When a design choice here looks strange, the
reason is almost always "the reference does it that way and the bytes have to match". Those places
are commented individually; §6 lists them together.

The guarantee is *directional*. The reference is upstream: if the two disagree, this is wrong until
proven otherwise, and the fix is here rather than there. The corpus's published pages on `w:/deals/`
and the notes site were generated by the reference, so a divergence is a visible regression.

## 2. Pipeline

```
                     source text (a buffer, not a path)
                              │
   parse.odin                 ▼
     normalise_newlines   CRLF and lone CR → LF                    §5.1
     expand_includes      #INCLUDE, one pass, via a callback       §5.3
     strip_comment_lines  lines starting //
     split_blocks         blank lines separate blocks
                              │
                              ▼  one block of text at a time
   content.odin
     classify_block       ORDERED tests, first match wins          §3
        │                 mutates Parse_State: #VUL #SEAT #+META
        ├── blocks.odin   list/enum/table/auction/diagram splitters
        └── bidtree.odin  ──► directives.odin  #CUT #COPY #PASTE #HIDE
                          ──► node.odin        indentation → tree
                          ──► call.odin        bid → canonical spelling
                              │
                              ▼
                       Document{ blocks, meta, diagnostics, arena }
                              │
   html.odin                  ▼
     render_html          blocks → element tree
        └── inline.odin   text → nodes (suits, emphasis, links)    §4
        └── xml.odin      element tree → bytes (ElementTree rules) §4
                              │
                              ▼
                            html string
```

## 3. Classification is ordered, and it is stateful

`classify_block` tries its tests in a FIXED ORDER and the first match wins. The order is not
cosmetic and cannot be sorted alphabetically or turned into a switch on the first byte:

1. headings, deepest marker first (`****` before `*`, since `**` also starts with `*`)
2. `-` lists — and a ` :: ` anywhere in the block makes it a description list instead
3. `#VUL`, `#SEAT` — settings, produce no block
4. `1.` enumerations
5. four call-shaped tokens in a row — an auction table
6. a bid table
7. `|` pipe table
8. a deal diagram
9. `#+KEY: value` metadata — produces no block
10. any other `#`-led block — a directive-only block, which usually yields nothing
11. anything with a non-space character — a paragraph
12. otherwise nothing

Several blocks satisfy more than one test. A bid table's first row starts with a digit, and so does
an auction table's first token; a diagram line starts with a letter, and so does prose. Reordering
these silently reclassifies real corpus content, and the failure is not a crash — it is a paragraph
appearing where a diagram used to be dropped, or a table rendering as prose.

**Blocks that are recognised and then not rendered still have to be classified correctly.**
`Diagram`, `Table`, `Bidding` and `Description` never reach html, in either implementation. It is
tempting to conclude that their detection does not matter. The opposite is true: if a diagram is not
detected it falls through to `Paragraph` (test 11 catches everything), and *then* it renders. The
cheapest parity bug to introduce here is a too-strict diagram matcher.

**Classification has side effects.** `#VUL`, `#SEAT` and `#+META:` mutate `Parse_State` as they are
passed, and every bid table built afterwards inherits the current vulnerability and seat. So blocks
must be classified strictly in document order, one at a time. This is why the loop in `parse` is not
parallel and must not become parallel — the work per block is a few microseconds anyway.

## 4. The html back end is two independent problems

### 4.1 Inline markup parses into the tree, not over the output

Suit glyphs, `*strong*`, `/em/`, `=code=` and `[label](target)` are turned into element nodes **as
text enters the tree**, never by rewriting serialised html. The reference moved to this approach and
the port keeps it, because it removes three whole classes of bug: the scanners never have to dodge
tags, the order of the passes stops mattering, and a link target — which by then has been normalised
into an anchor id — is never mistaken for a suit run. That last one is why an opponent's bid in
parens renders its glyph instead of being suppressed by a lookahead that existed to protect markup.

Two layers, because the constructs nest and the substitutions do not:

- `find_inline` finds the leftmost construct that can CONTAIN more markup: link, strong, em, code.
  At any one position the alternatives are tried in the reference's order, so `[` beats `*`. The
  content is then filled recursively.
- `write_plain` handles what cannot nest: digit-led suit runs, the `!x` shorthand, and long dashes.

### 4.2 `xml.odin` exists to be byte-compatible with `ET.tostring`

It is not a general XML library and should not grow into one. It reproduces exactly the behaviours
the goldens depend on:

- **text and tail.** An element has `text` (before its first child) and every child has `tail` (the
  text after it). Mixed content — a bid `<div>` followed by loose description text inside the same
  `<li>` — is only representable this way, and putting text in the wrong slot is invisible in the
  tree and obvious in the output.
- **`<tag />`,** with a space before the slash, for an element with neither text nor children.
- **attribute order is insertion order.** Hence a list, not a map.
- **US-ASCII with decimal character references.** `ET.tostring` with no `encoding` argument
  serialises as us-ascii with `xmlcharrefreplace`, so every non-ascii character becomes `&#9827;`
  and friends. The published pages contain no utf-8 bytes at all.
- character data escapes `&`, `<`, `>`; attribute values escape those plus `"`, and turn CR, LF and
  TAB into numeric references.

## 5. Where this deliberately differs from the reference

### 5.1 CRLF is normalised on the way in

The corpus is CRLF. Python's text mode converts that to `\n` while reading, invisibly, so the
reference never had to think about it. Everything downstream here — the blank line that separates
blocks, the indentation that nests a table — is written against `\n`.

This is worth knowing because of how it fails. A CRLF document with no normalisation does not error:
`split_blocks` finds no separator, the entire file becomes ONE block, that block starts with
`#+TITLE:` so it classifies as metadata and produces nothing. The output is a structurally valid
page with a correct `<title>` and an empty body. It reads like a broken renderer rather than a line
ending problem. `test_crlf_source_parses_the_same_as_lf` pins it.

### 5.2 No global state

The reference keeps `content`, `clipboard`, `vulnerability`, `seat` and `meta` at module scope.
`content_from_file` resets them on entry, which makes a single conversion correct and concurrent
conversions impossible; the notes build therefore spawns one python process per file. Here that
state is `Parse_State`, created per parse. Two parses cannot see each other, and the build can do
all 19 files in one process.

### 5.3 Source text and an include callback, not a path

`parse` takes a string. This is the whole reason the port exists: a live preview renders the buffer
someone is still typing, which has not been saved anywhere.

`#INCLUDE` follows from that. The reference opens the named file relative to the process's working
directory — which is why `apps/quiz/quiz.py` has to `chdir` around every parse. Here it is a
callback (`Include_Resolver`), so a caller can serve includes from a directory, from open editor
buffers, or refuse them. Refusing leaves a diagnostic and drops the directive.

Expansion is ONE pass over the original text, so an include inside an included file is not expanded.
That matches the reference, where `re.sub` scans the string it was given rather than its own output.
Nested includes never worked; this is not a regression to fix quietly.

### 5.4 Errors are data

`Parse_State.diagnostics` collects problems that do not justify refusing the document, and they end
up on `Document.diagnostics`. The motivating case: `#PASTE` of an unknown name raises `KeyError` in
the reference and takes the build down with a traceback. A preview parses half-typed text on every
keystroke, so it degrades instead.

Nothing else about the parse changes. A document with diagnostics still renders.

### 5.5 A diagnostic carries a POSITION, and the map that gives it one

`Diagnostic` is `{message, severity, file, line, col, length}`, not a sentence — an editor needs a
range to squiggle and a build log needs the line in front of the sentence (`diagnostic_text` writes
that form). `line`/`col` are 1-based, `col`/`length` are bytes, and a zero is "not known": no line at
all, or the whole line, or to the end of it.

The hard part is that **the parse does not walk the text the caller handed over**. Newlines are
normalised, `#INCLUDE` is expanded, comment lines are dropped — so a working-line number is not a
buffer-line number, and inside an included region it belongs to a different file entirely. Aligning
the two texts afterwards would be guesswork, so instead `positions.odin`'s `Mapped_Builder` records
each line's origin AS THE BYTES ARE WRITTEN: the passes stay byte-for-byte what they were (parity
would notice otherwise) and gain an origin table alongside their output. `span_at_offset` turns any
offset in the working text into a source span; `span_of` does the same for a string the classifier is
holding, using the fact that blocks and rows are SUBSLICES of the working text. A string that was
BUILT rather than sliced — a paste's output, a cloned paragraph — is detected by pointer range and
reported with no position rather than a wrong one.

The one limitation, taken deliberately: a source with LONE `` line endings is counted after
normalisation, so its numbers shift. CRLF and LF are exact.

### 5.6 Checks that report without changing anything

`checks.odin` holds the diagnostics that exist for an editor rather than for the parse. They only
append to `diagnostics`, so the html is identical whether they run or not and corpus parity cannot
see them.

* **An unknown directive** — `#HDIE` is not a directive, so the block falls through to the bid table
  builder, produces no rows and is DROPPED from the output in silence. The check knows the
  reference's whole list (`INCLUDE`, `CUT`/`ENDCUT`, `COPY`/`ENDCOPY`, `PASTE`, `HIDE`, `BIDTABLE`,
  `VUL`, `SEAT`, plus `#+KEY:` metadata) and underlines the keyword. Zero of these in the corpus,
  which is the result that makes it worth keeping.
* **A cross-reference that resolves nowhere** — `[label](#Anchor)` against the anchors the headings
  actually generate, both ends through `normalise_header_id`. OFF unless
  `Parse_Options.check_cross_references` asks for it, because the corpus is chapters assembled by a
  root document: a chapter opened alone links to headings that exist in a file it does not include.
  Measured on the corpus: **13 genuinely broken anchors in the assembled `bidding-system.bml`**.

## 6. Bug-compatibility, on purpose

Each of these looks like a defect, is reproduced deliberately, and has a test pinning it. Do not
"fix" one without regenerating the published pages, because each is visible in them.

| behaviour | why it happens |
|---|---|
| `**bold**` → `<strong><strong>bold</strong></strong>` | the content pattern is `\S(?:[^*]*\S)?` and that trailing `\S` matches an asterisk quite happily, so the outer match takes `*bold*` as its content and the recursive fill finds emphasis again |
| a list item keeps its trailing newline, so `<li>` closes on the next line | an item runs to the START of the next marker's line; the newline belongs to the item before it |
| `<title>` is emitted at the END of `<head>` | the reference appends it after the entire body has been built |
| `1NT` stays literal text, `2N` becomes `2NT` | `N` counts as a suit letter only when not followed by `T`, so the run match fails on `1NT` altogether |
| `#CUT` pairs with the LAST `#ENDCUT` in the block, not the nearest | the reference's `(.*)#ENDCUT` is greedy under `DOTALL` |
| `normalise_header_id("  x  ")` → `"__x__"` | spaces become underscores BEFORE the strip, so there is nothing left to strip |
| `#BIDTABLE` only works at the very start of a block | that substitution is anchored to the start of the string, not to each line |

## 7. Scanners, not regular expressions

The reference is built on regex; this is not, and the reason is not taste.

**It relies on lookaround in eight places** — `(?<![^\s>])` before `*strong*`, `(?<!\S)` before `/em/`
and `=code=`, `N(?!T)` in the suit run, `(?![A-Za-z])` after a bare `P`/`X`/`R`, `(?=--|\s*=)` in
the bid-table sniffer, `(?<=\|)` in the pipe table. **Neither available engine supports lookaround.**
`core:text/regex` has no lookaround at all (its flags are Multiline, Case_Insensitive,
Ignore_Whitespace, Unicode; ten capture groups maximum). `rure` — the Rust regex crate, via the
`odin-rure` bindings — does not either, and says so in its own README: linear-time automata engines
give up lookaround and backreferences by construction.

So those patterns need rewriting whichever engine is used, which means a regex engine buys no
transcription fidelity. What hand-written scanners buy instead:

- **no dependency.** The library is `core:`-only, so it can be vendored as pure Odin. Linking
  `rure.lib` into it would push a static library into the workbench too — the opposite of the
  deployment goal this port serves.
- **one pass.** The reference makes roughly thirty regex passes over the text.

Where the port must reproduce a regex's *behaviour* rather than its intent, the comment says so.
`match_delimited` is the clearest case: it searches for the closing delimiter from the furthest
candidate inwards, because that is what greedy matching with backtracking does, and `*one*` only
parses correctly after falling back past the delimiter-as-content reading.

## 8. Memory

**One arena per `Document`.** Everything the document points at — block text, list items, every
`Node` — is allocated from it, so `destroy` is a single wholesale free. Nothing is walked and
nothing is reference-counted. This is what makes re-parsing on every keystroke cheap: the previous
document's teardown is a pointer reset.

`render_html` builds its element tree in its OWN scratch arena and frees it on return; the tree
exists only to be serialised. Only the returned html string is allocated from the caller's
allocator.

Consequences worth knowing:

- A `Block`, a `Node` or a `string` taken out of a `Document` dies with it. Copy before `destroy`.
- The library never frees an individual allocation, so the internals do not need to be careful about
  intermediate garbage — they *are* careful about the amount of it, since the arena grows.
- `context.temp_allocator` is used for genuinely transient work inside a single procedure only.

## 9. Working on it

### Parity, and how to debug a failure

`just parity` renders every corpus file with both implementations and compares bytes. It needs two
checkouts that live outside this repository — the corpus (`BRIDGE_DIR`) and the reference
(`BML_TOOLS_DIRECTORY`) — and reports "skipped" when they are absent, so it is safe to run anywhere.
Each file goes through a fresh python process, because the reference cannot convert two documents in
one.

On a mismatch it prints the byte offset of the first difference and 60 bytes of context from each
side. That is usually enough to name the construct. From there:

1. Reduce it to a few lines of BML that still differ.
2. Get the reference's answer directly, rather than reasoning about its regexes:
   ```
   python -c "import sys;sys.path.insert(0,r'~/dev/bml');import bml2html as h,xml.etree.ElementTree as ET
   p=ET.Element('p');h._fill(p,'**your text**');print(ET.tostring(p).decode())"
   ```
3. Add it to `html_test.odin` or `bidtree_test.odin` with the reference's output as the expectation,
   then fix.

Step 2 is not optional. Every parity bug found during the port came from *reading* a regex and
getting it subtly wrong; running it took seconds and settled the question.

### What the unit tests cover that parity cannot

The clipboard directives — `#CUT`, `#COPY`, `#PASTE`, `#HIDE`, `#BIDTABLE` — and `#VUL`/`#SEAT`
appear **nowhere** in the corpus. Only `#INCLUDE` does. Parity can therefore never exercise them,
and nothing else in the project would notice if they broke. Their expected values in
`bidtree_test.odin` were captured by running the reference on those exact inputs, and that is how
any further case should be added.

### Extension points

- **Another back end** (the reference also has LaTeX and BSS, not ported): a new file beside
  `html.odin` reading `Document.blocks`. No parser change. `xml.odin` is html-shaped only in that it
  emits `<tag />` the way ElementTree does.
- **A new block kind**: add to `Content_Kind`, add a splitter in `blocks.odin`, and insert the test
  into `classify_block` **at the right position** — §3.
- **A different include policy**: pass a different `Include_Resolver`. The library never touches the
  filesystem itself; `examples/render.odin` is the file-reading one.

### Performance

Measured on this corpus, in-process, `-o:speed`:

| | this | reference |
|---|---:|---|
| one chapter (`nt-bidding.bml`) | 1.9 ms | 29 ms + interpreter start + process spawn |
| whole system, 1.2 MB of html out | 17.6 ms | 262 ms + the same |

The reference's per-file process spawn is not incidental — it is forced by the module-level state
(§5.2), so the notes build pays interpreter startup nineteen times.

If this ever needs to be faster, the honest answer is that it probably does not: 1.9 ms is well
inside a keystroke. The arena and the single pass are already the two decisions that matter, and
`render_html`'s element tree is the one remaining obvious allocation — it could be serialised
directly, at the cost of making the text/tail rules (§4.2) implicit rather than explicit. That trade
is not worth it at these numbers.
